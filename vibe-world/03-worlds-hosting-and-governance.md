# Worlds, Hosting, and Governance

## Core idea

The game should function as a network of player-created worlds or servers.

A player can create a world from a 3D template, choose a ruleset, and become that world’s host.

This makes governance part of the product, not just background moderation.

## World creation flow

A simple creation flow could be:

1. choose a template,
2. name the world,
3. choose public or private,
4. choose a rule preset,
5. choose persistence model,
6. launch the world.

## World templates

Examples of starting templates:

- floating island,
- cozy room,
- plaza,
- obstacle island,
- empty terrain,
- social lounge.

## The host role

The world creator becomes the **host**.

The host has more power and control than ordinary players.

### Host capabilities

Potential host powers include:

- choose world rules,
- choose persistence/reset cadence,
- enable or disable destructive editing,
- define world vibe/preset,
- configure optional protected spawn area,
- moderate disruptive players,
- reset zones or full world,
- appoint moderators/co-hosts later,
- curate or theme the world.

### Host authority vs platform authority

Hosts should have strong local power, but not absolute power over platform-wide safety constraints.

The platform still enforces:

- safety moderation,
- anti-crash protections,
- spam limits,
- hard resource limits,
- prohibited content rules.

## Public vs private social contracts

### Public hosted world

A public hosted world is:

- discoverable,
- socially persistent or cyclical,
- more curated,
- less grief-prone,
- appropriate for recurring communities.

### Private hosted world

A private hosted world is:

- invite-only or limited access,
- more experimental,
- more disposable,
- more open to chaos and destruction.

## Rule presets

In V1, the easiest path is likely **presets plus a few toggles**, not fully custom rule programming.

### Example presets

- Cozy Public
- Collaborative Remix
- Curated Showcase
- Private Chaos
- Friends Build Night

### Example toggles

- destructive edits: on/off
- object cooldown: 10s / 30s / 60s
- remix others’ objects: yes/no
- persistence: permanent / temporary / reset
- max players: 8 / 16 / 32

## Persistence models

### Permanent

The world keeps evolving unless manually reset.

### Temporary

The world is session-like and disposable.

### Scheduled reset

The live world resets on a timer, while prior versions remain explorable as read-only snapshots.

## Why reset cadence matters

Reset cadence is not just a technical setting. It becomes part of the world’s identity.

Examples:

- hourly reset world = rapid experiment lab,
- daily reset world = daily collaborative art jam,
- weekly reset world = evolving event space,
- monthly reset world = seasonal public world.

## Discovery and popularity

The strongest product shape is that players discover and join the most fun worlds.

Popularity should not be based only on raw concurrent users. Better signals include:

- current population,
- returning visitors,
- average session length,
- low moderation friction,
- recent activity,
- social reactions,
- host reputation,
- world stability.

## World browser metadata ideas

Useful world browser fields might include:

- world name,
- template,
- mode (public/private),
- reset cadence,
- player count,
- tags or mood,
- created by host,
- age of live cycle,
- number of archived versions,
- currently trending or featured.

## Governance philosophy

The platform should encourage a spectrum of world cultures rather than enforcing one style:

- stable curated worlds,
- collaborative build worlds,
- disposable experiment worlds,
- social hangouts,
- event-based themed worlds.

That diversity is one of the most interesting long-term strengths of the idea.
