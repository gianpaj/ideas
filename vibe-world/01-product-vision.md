# Product Vision

## One-line concept

A network of player-created 3D worlds where anyone can vibe code chunky voxel objects and environments together in real time.

## Product thesis

Most UGC games ask players to either:

- learn a full creator toolchain,
- place assets manually for too long,
- or play inside worlds whose rules are fixed in advance.

This project aims for a different feeling:

- **prompt-first creation** instead of full manual modeling,
- **social remixing** instead of isolated building,
- **world-specific governance** instead of one universal rule set,
- **chunky voxel readability** instead of fragile realism,
- **ephemeral + persistent world types** instead of only one mode.

The game is not just “a sandbox.” It is a **platform of hosted worlds** with distinct cultures, reset rhythms, and permission models.

## Core fantasy

The player fantasy is:

> “I can enter a strange 3D world, speak or type an idea, see a rough blocky version appear instantly, reshape it for a few seconds, and release it into a shared world that other people can remix.”

The host fantasy is:

> “I can launch my own social world from a template, define its vibe and rules, and become known for running the most fun or most beautiful world.”

## Design pillars

### 1. Prompt-first, not CAD-first

The primary interaction is not painstaking 3D modeling. The main loop is:

- select place or object,
- describe a change,
- get a rough draft,
- lightly refine,
- release it to the world.

### 2. Chunky voxels as identity

The world should look obviously blocky and voxel-native. This is a feature, not a compromise. The chunky visual language supports:

- quick readability,
- low-tedium iteration,
- clear multiplayer diffs,
- easier AI constraints,
- stronger visual brand.

### 3. Shared worlds with local rule sets

The platform hosts many worlds, and each world can feel socially different because the host chooses:

- public vs private,
- persistence model,
- reset cadence,
- remix/destruction permissions,
- atmosphere and curation style.

### 4. Collaboration before competition

The first version is a **social sandbox**, not a combat game or progression-heavy survival game. The fun comes from:

- co-creation,
- remixing,
- discovering worlds,
- reacting to other people’s ideas,
- seeing worlds evolve over time.

### 5. Freshness through resets and archives

Some worlds should persist. Others should wipe on a schedule. Reset worlds are intentionally ephemeral in the live present, but old versions remain explorable as read-only historical snapshots.

This creates a world network that is part sandbox, part social venue, part memory museum.

## What the game is not trying to be in V1

- a photoreal UGC engine,
- a full in-game Blender,
- a general-purpose scripting IDE,
- an MMO progression economy,
- a high-fidelity physics sandbox,
- a combat-first PvP game.

## Product shape

The overall product can be thought of as four layers:

### Layer 1 — Platform

A discovery and hosting layer for player-created worlds.

### Layer 2 — World governance

Each world has rules, permissions, persistence, and a host.

### Layer 3 — Live object creation

Players create and remix voxel objects through prompts, commands, and transforms.

### Layer 4 — Memory and archaeology

Reset worlds leave behind explorable read-only versions.

## Emotional goals

The worlds should feel:

- playful,
- improvisational,
- low-pressure,
- social,
- weird in a charming way,
- alive in the present,
- occasionally haunting in archive mode.

## Why the social sandbox route is right for V1

A social sandbox is a better first proving ground than a deeper game genre because it validates the hardest new pieces first:

- prompt-to-object latency,
- multiplayer sync,
- object governance,
- edit conflict handling,
- moderation and permissions,
- fun of collaborative creation,
- host/world discovery dynamics.

If that layer works, challenge modes, puzzle modes, parkour, or other objective-based experiences can be built on top later.
