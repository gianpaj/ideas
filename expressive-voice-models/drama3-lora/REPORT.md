# Drama 3 LoRA feasibility

2026-11-07 · [Architecture](ARCHITECTURE.md) · [Smoke test](SMOKE_TEST_PLAN.md) · [Sources and evidence](SOURCES.md)

**The full-model LoRA smoke test requires larger hardware.** Start with one dedicated 80 GiB-class GPU for the BF16 reference path, batch 1 and at most 256 rows. Budget 96 GiB if the first hardware allocation must absorb uncertain workspace use. The missing code is a cache-free training forward that returns all ten heads with the right shifts and masks. A published 16 GB Turkish experiment trains a reduced expert bank one layer at a time. That provides a reusable weight reader and a useful bound on a different workload. [Turkish training entry point](https://github.com/kasparovabi/drama-3-tr/blob/b8be96dbb0d280d98f1d585ea4dd0a48f0d89799/exp3_distill.py)

## What to try before training

Drama 3 already generates multilingual speech, including Japanese, and understands ordinary-language directions. Fish Audio demonstrates point cues such as `[laughs]` and `[sighs]`, scoped delivery, and natural-language style cues. These are prompt text. Speaker markers are reserved tokenizer entries. Laughter cues use ordinary text tokens. Test tagged and plain prompts with the same words and reference first. Fine-tuning has a concrete purpose when a cue repeatedly lands in the wrong place, changes the wrong part of the line, is ignored in the target language, or disrupts speech. Try a cough as a listening probe; the Japanese release has coughing and throat-clearing examples, with no measured reliability for either release. [Base examples](https://huggingface.co/fishaudio/drama-3/blob/78e5ab79e49aa9a25abe8799eff2c4d73a1c3216/README.md), [control syntax](https://arxiv.org/html/2610.18010v2#A3), [Japanese tag inventory](https://huggingface.co/Aratako/Drama-3-Japanese/blob/e3762febfc794eaa1d08ee9931215365f92968a8/TAG_LIST.md)

The smoke test asks for a brief audible laugh at a mid-line boundary in English. Sentence completion and ordinary delivery are controls. Language adaptation is a separate task. Improving Japanese readings would require a corpus and evaluation designed around reading ambiguity, while broader expressivity would need diverse labeled examples and listening tests. A tiny run can establish that the loader, labels, loss, optimizer, and export work. A held-out comparison can expose obvious failures.

## Event cues and public audio

A point cue belongs at the boundary where the speaker makes the sound. For `I packed everything. [laughs] Except the tickets.`, the user turn contains that text and the assistant target contains the same speaker saying both phrases with an audible laugh between them. The frozen codec encodes the whole take, including the laugh. The speech losses train on those target codes and EOS. Event timestamps help prepare and evaluate the examples. The model receives the inline cue and the target codes, with no separate event target in the published Drama 3 recipe. Fish Audio's instruction SFT keeps plain speech in the mix and uses natural-language cues. Its later preference training is a separate stage. [Fish Audio report §§3.1–3.3](https://arxiv.org/html/2610.18010v2#S3)

Treat an isolated laugh, speech delivered while laughing, and a cheerful line as separate controls. Use a point cue for the first, a scoped or line-level instruction for the second, and a style prefix for the third. Keep overlapping speech-laugh examples out of the isolated point-cue set. Aratako's tag inventory distinguishes `[笑い]` from `[笑いながら]`, with automatically annotated training tags. The Japanese corpus and labeling process are undisclosed. [Drama 3 control syntax](https://arxiv.org/html/2610.18010v2#A3) · [Japanese tag inventory](https://huggingface.co/Aratako/Drama-3-Japanese/blob/e3762febfc794eaa1d08ee9931215365f92968a8/TAG_LIST.md)

If `[laughter]` is an app-facing spelling for the existing behavior, map it to the documented `[laughs]` before sending the text to Drama 3. Compare the spellings and a plain version on the same prompts, voices and seeds. For a behavior the base repeatedly misses, gather real audio with the event in context. Keep the literal transcript, the event type and onset/offset, the word boundary, and who made the sound. Pair some examples with the same words spoken plainly. Inspect the full target audio for crosstalk, silence trimming and ASR corrections that delete sounds. Split by speaker and source recording. Use held-out listening to score event presence, placement, unwanted events and whether the sentence finishes. [NoVA placement benchmark](https://github.com/ira-rumik/nova-bench) · [NVV-SuperBench broader prompt set](https://github.com/lmxue/NVV-SuperBench)

For an English pilot, **AMI is the first public source to inspect for natural in-context laughs**. Its transcript layer includes timed vocal events and the corpus offers individual headset channels. Of 16,524 laugh annotations, 9,686 have positive duration and 138 pass a strict screen for nearby words on both sides in the same channel. Those are candidates for listening, with no overlap or audio-quality checks yet. The same screen yields five coughs and one sigh. For those tags, prioritize separately recorded examples or audit another corpus. **NonverbalTTS** offers closer-to-ready tagged utterances for non-commercial research. **Open Yap** offers cleaner conversational channels and machine transcript candidates if we can label them and respect the publisher's request about identifiable voices. **VocalSound** provides isolated sounds for calibrating detectors and listening criteria. Its isolated clips cannot establish where a laugh fits between words. [Dataset details and terms](SOURCES.md#data-sources-for-event-tags)

Other projects sometimes change the tokenizer. The NonVerbalSpeech-38K authors gave F5-TTS vocabulary entries for event tags. An OmniVoice case study also reports dedicated entries and substantial variation in event adherence by reference voice. Those are results for their own models. Drama 3 already uses ordinary text for directions. Test its native cues and improve aligned data before expanding its vocabulary. [F5-TTS experiment](https://arxiv.org/html/2508.05385v2#S4.SS1) · [OmniVoice case study](https://www.ahmadwaqar.dev/work/omnivoice-nonverbal-tts)

### Japanese evaluation

- **Reading.** No references or captions. Target reading accuracy 92.021% → 93.188%, kana CER 7.474% → 6.548%, sentence kana CER **1.421% → 2.087%**. Standard text CER 5.699% → 5.572%. 66,423 of 67,680 paired takes met the shared 1–10 s filter.
- **JVS cloning.** Mean CAM++ similarity 0.7333 → 0.7280 (one reference) and 0.7769 → 0.7688 (three). ERes2Net similarity also declined. ERes2Net top-1 increased with one reference (95.83% → 96.67%). Whisper CER moved 2.886% → 3.082% for one reference and 3.023% → 3.008% for three. The joint 1–20 s filter retained 2,492/2,500 and 2,429/2,500 pairs, respectively.
- **Interpretation.** The comparisons used five samples per item, SGLang-Omni `b658fa6…`, temperature 1, top-p 0.9, top-k 30 and 2,048-frame cap. Joint filtering removes pairs in which either model failed and leaves each model's individual failure rate unknown. ASR scores lexical accuracy and may ignore or misread laughs, breaths and coughs. The demonstrations and tag list provide examples, without an adherence benchmark. [Japanese benchmark protocol](https://huggingface.co/Aratako/Drama-3-Japanese/blob/e3762febfc794eaa1d08ee9931215365f92968a8/README.md#-benchmarks)

| Small and Expressive Medium        | Small keeps 256 experts in four layers, 100 in the other 36, about 45% of slots. | Other inference quants             | Jmica's V2 converts the Oct 29 weights, V1 pins Oct 13. Supported conversion is from checkpoint to GGUF. A trainable reconstruction must explicitly unpack expert tensors, restore supported head semantics and validate backward. ComfyUI packed-safetensor loaders and `drama-3-int4` likewise give serving paths, with no demonstrated Drama 3 training backward.                                                                                                                                                                                            |

PEFT's `target_modules` can match real dense linears such as `self_attn.o_proj`, `linear_attn.out_proj` and shared expert projections. Its documented 3-D `target_parameters` feature requires actual parameters with the expert axis first. Native FP8 banks are buffers, while BF16 banks are parameters. The fused BF16 parameter path would still need checking for materialized deltas, memory, and compatibility with the custom grouped forward. The proposed smoke test uses four explicit LoRA wrappers, avoiding expert adaptation. bitsandbytes `Linear4bit` is a candidate for compatible dense layers only. Its usual loader cannot transparently convert these expert banks. TRL/Axolotl cannot supply the two-head-family causal forward and loss just by swapping in a checkpoint. Budget **about 70–75 GiB** for the 80 GiB smoke path under these assumptions. Fallback kernels and longer sequences can exceed it. A100 80 GiB is a candidate for the BF16 reference backend without native W8A8. H100 80 GiB also lets the same machine compare native FP8 serving. A 96 GiB RTX PRO 6000 adds headroom. A later mixed-precision experiment could keep the 36 frozen prefix layers in FP8 and the four gradient-bearing layers in BF16. That puts model storage at about 39.9 GiB. A 48 GiB Ada or newer GPU becomes a candidate after implementing a mixed loader and measuring the gradient-bearing suffix. Compare it with the all-BF16 reference before drawing a quality conclusion. The provider lists $1.79/h for A100 80 GB, $2.89–3.99/h for H100 80 GB, and $2.49/h for RTX PRO 6000 96 GB. A hypothetical 2–4 GPU-hour allocation is about **$4–16 compute-only**, excluding storage and queue time. This is an allocation estimate, with no timing extrapolated from inference or purchase made. [Runpod Pod pricing](https://www.runpod.io/pricing)

**Local snapshot.** RTX 4060 Ti, driver 595.91.07, 16,380 MiB total, 8,725 MiB used and 7,223 MiB reported free. Ollama used 7,814 MiB and the voice-agent Python process 864 MiB. The host showed 30,443 MiB RAM, 13,607 MiB available, and 7,502 of 8,191 MiB swap in use. About 405 GiB of filesystem space was free in the workspace. This was a read-only snapshot, with no local load or performance measurement. CPU-resident FP8 experts alone need 30 GiB before scales and live RAM use. At a theoretical 4 bits per expert weight the banks still take 15 GiB before scales, plus 6.87 GiB of other BF16 weights. That exceeds the dedicated card before activations, and exceeds the observed free GPU plus available host RAM even with split placement. A dedicated 16 GiB GPU plus disk-streamed frozen-prefix features and a one-block or tower-only adapter is a narrower research path. It trades disk I/O and a separate prefill/serving implementation for memory. It is unverified here and would still need an isolated GPU budget.

## Next steps in impact order

1. **Implement and prove the training forward.** Add the shifted, cache-free teacher-forced pass in a separate experiment directory. Match instrumented native per-position logits and pass suffix-causality, gradient and parameter-delta checks on one example.
2. **Measure residency on a dedicated GPU.** Record load peak and one-step CUDA peak on an 80 GiB-class GPU before starting a longer job. If that reference path misses budget, measure 96 GiB or move the frozen prefix out of the backward job. Keep the current GPU services running.
3. **Determine whether there is a behavior worth changing.** Render pinned base controls on the proposed consented split. Confirm the failure mode before assigning held-out adherence targets.
4. **Resolve the Japanese reproduction gap.** Look for a published training commit, exact base SHA, adapter target/optimizer manifest, and one redacted collated example. Dataset and compute provenance are required for a Japanese reproduction; the adapter-only smoke test can proceed with its own documented contract.
5. **If 16 GiB is the target, prove one bounded variant.** Cache frozen-prefix features with a disk-aware loader and compare the remaining differentiable block's logits and gradients to BF16. Measure host and device peaks with live services accounted for before considering full-model quantized backward.
